# Interactive, Idempotent Installation

**Date:** 2026-08-03
**Status:** Approved, ready for implementation planning

## Problem

`make install` bakes machine-specific settings into the build and fails in ways
that are hard to diagnose:

1. **Fixed listener.** `config/monitor.conf` ships `LISTEN=0.0.0.0:8443`. When
   another service already owns that port, installation reports success and
   leaves a service that never starts. Nothing in `install.sh` checks the port.
2. **Fixed allowed networks.** `ALLOWED_CIDRS` ships a specific site subnet,
   hardcoded a second time as a fallback in `internal/app/config.go`. Installed
   on any other network, the web interface rejects every client. This is more
   damaging than the port conflict because the service *does* start.
3. **Site data in the repository.** That same subnet is committed across the
   config, the Go default, the Makefile help text, both READMEs and both
   installation guides. It describes the maintainer's private network topology
   and is published on GitHub.
4. **Opaque build failures.** `make build` checks only for `clang` and
   `bpftool`. A missing PAM development header surfaces as a C compiler error
   in the middle of a Go build, and a missing Node toolchain surfaces later
   still. Neither message names the package to install.
5. **Not re-runnable.** `install.sh` skips `monitor.conf` when it already
   exists, so there is no supported way to change the port other than editing
   the file by hand. Certificates are generated by a separate target, so
   `make install` alone never produces a working system.

## Goals

- `make install` asks for the settings that genuinely vary between machines and
  produces a working system on its own.
- Re-running `make install` completes cleanly and preserves manual edits.
- Automated installs keep working without a terminal.
- Build prerequisites are reported once, up front, with the command that fixes
  them.
- No site-specific values remain in the repository.

## Non-goals

- Installing system packages automatically.
- Choosing a substitute port without the operator's consent.
- Any change to the runtime behaviour of the monitor or agent beyond reading
  the values it already reads.

## Design

### Configuration resolution

Every prompted setting resolves through one chain, used identically in
interactive and non-interactive mode:

```
environment variable  >  existing installed config  >  autodetected  >  built-in default
```

The chain produces a *default*. In interactive mode that default is offered as
a prompt the operator can accept with Enter; in non-interactive mode it is
applied silently. A setting supplied through the environment is never prompted
for.

| Setting | Environment | Autodetected from | Built-in default |
|---|---|---|---|
| `LISTEN` | `LISTEN` | — | `0.0.0.0:8443` |
| `ALLOWED_CIDRS` | `ALLOWED_CIDRS` | global IPv4 interfaces, excluding docker and veth, plus loopback | loopback only |
| `HOSTS` (certificate SAN) | `HOSTS` | existing certificate SAN, else hostname and local addresses | hostname |

Each answer is validated before use: the listener must be `host:port` with a
port in 1–65535, every CIDR entry must parse, and every certificate host must
be a valid IP address or DNS name. An invalid interactive answer re-asks the
same question; an invalid environment value aborts with a message naming the
variable.

`install.sh` runs non-interactively when stdin is not a terminal. This keeps
`curl | sudo bash` and CI installs working.

### Port conflict detection

The installed monitor holds the configured port whenever the service is
running, so a naive "is this port free" test would report a conflict on every
upgrade. Detection therefore identifies the holder before deciding. Whether a socket
exists and who owns it are established separately, because ownership requires
privilege and the socket's existence does not:

1. Determine whether anything listens on the chosen port.
2. Look up the listener's owning process.
3. If the owner belongs to the monitor's own systemd unit, there is no conflict
   — continue silently.
4. A listening socket whose owner cannot be identified counts as a conflict.
   The socket is real regardless of whether we are permitted to see who opened
   it, so treating it as free would recreate the failure this change exists to
   prevent.
5. Otherwise there is a real conflict:
   - **Interactive:** report the owning process by name and PID, offer the
     first free port above the chosen one, and ask whether to use it.
   - **Non-interactive:** abort, naming the process that holds the port and the
     `LISTEN=` variable that overrides it. No port is chosen automatically.

### Idempotent config writes

`monitor.conf` is updated key by key. Only the keys whose values changed are
rewritten, in place; comments, ordering and unrelated manual edits survive. A
key that is absent from the file is appended under the section it belongs to.

Writes are atomic — a temporary file is populated and then installed over the
target with the existing ownership and mode — so an interrupted install cannot
leave a truncated config. A `.bak` copy is taken before the first modification
of an existing file.

### Certificate generation

When no certificate exists, `install.sh` generates one from the resolved
`HOSTS` value, so `make install` alone yields a system that starts and serves.
An existing certificate is left untouched; `make cert-generate` remains the way
to replace one deliberately.

### Service restart

`install.sh` ends with a `try-restart` of the monitor and agent units, so a
changed port or CIDR list takes effect immediately. `try-restart` is used
rather than `restart` so a first-time install does not start services the
operator has not enabled yet.

### Dependency preflight

A new `deps-check` target runs before `build`. It verifies the presence of the
Go toolchain, a C compiler (both cgo dependencies need one), Node and npm,
`clang`, `bpftool` and `llvm-strip`, and — critically — the headers that
currently fail mid-compile: the PAM application header used by
`internal/auth`, and the libbpf helper headers included by the BPF program.

Missing items are collected and reported together, mapped to package names for
the detected package manager (`apt`, `dnf`, `pacman`), followed by a single
command that installs all of them. On an unrecognised package manager the
report lists the missing binaries and headers without package names. Nothing is
installed automatically.

`deps-check` is also exposed as a standalone target so the fix can be verified
without starting a build.

### Removing site data from the repository

The committed subnet is replaced everywhere it appears:

- `internal/app/config.go` — the hardcoded fallback becomes loopback only. This
  is fail-closed: a config that fails to specify allowed networks grants local
  access rather than silently exposing the service to a network the operator
  never named.
- `config/monitor.conf` — ships loopback only, with a comment directing the
  operator to the installer or to edit the value.
- `Makefile` help, both READMEs and both installation guides — examples use
  RFC 5737 documentation addresses (`203.0.113.0/24`, `203.0.113.10`), which
  are reserved for documentation and route nowhere.

The generic `10.0.0.0/8` in `internal/app/config_test.go` is test data, not site
data, and stays.

Real values are written only to `/etc/system-maintenance/monitor.conf` at
install time. That path is outside the repository and cannot be committed.

## Testing

- **Config merge:** updating one key preserves comments, ordering and unrelated
  keys; a missing key is appended; the pre-write backup exists; an interrupted
  write leaves the original intact.
- **Resolution chain:** each source wins over the ones below it, for each of
  the three settings.
- **Validation:** malformed ports, CIDRs and certificate hosts are rejected;
  a malformed environment value aborts rather than falling through to a
  default.
- **Port detection:** a port held by the monitor's own unit is not a conflict; a
  port held by anything else is; the non-interactive path aborts rather than
  reallocating.
- **Dependency preflight:** with a dependency masked from `PATH`, the report
  names it and the run stops before the Go build starts.
- **Go defaults:** `DefaultConfig` and a config file that omits
  `ALLOWED_CIDRS` both yield loopback-only access.
- **End to end:** a second `make install` over an existing installation
  completes without error and without changing accepted values.

The project has no shell test harness today and this change does not introduce
one. The config-merge, resolution-chain, validation and port-detection logic is
therefore extracted into functions that a plain bash test script can source and
call directly, and that script runs as a new `make test-install` target wired
into `make test`. The Go default change is covered by the existing
`internal/app` test suite.

## Risks

- **Tightening the Go default changes behaviour** for any deployment relying on
  the old hardcoded fallback while omitting `ALLOWED_CIDRS`. The installed
  config always sets the key explicitly, so this affects only hand-built
  configs. It is called out in the release notes.
- **Listener ownership lookup requires privilege.** `install.sh` already runs as
  root, so the owning PID is visible. Where it is not, the installer reports the
  port as held by an unidentified process rather than assuming it is free.

- **Prompt loops must be bounded.** A validator that can never be satisfied, or
  a terminal that returns EOF on every read, would otherwise spin forever. The
  prompt gives up after a fixed number of attempts and fails the install.
